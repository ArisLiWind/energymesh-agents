# EnergyMesh Agents

团队：超境创新

赛道：GOAI Agent Infra「新智基座」

## 1. 项目一页纸

EnergyMesh Agents 是面向园区微电网与储能运营场景的多 Agent 调度策略系统。项目聚焦一个真实业务痛点：不同园区的光伏、储能、充电桩、负荷优先级、电价规则和安全边界差异很大，传统交付往往需要为每个客户单独编写策略代码，导致交付慢、复用差、策略调整成本高，也缺少可验证、可审批、可审计的闭环。

EnergyMesh Agents 不是让大模型直接控制电力设备，而是基于 AgentTeams 构建「调度 Agent、执行 Agent、审计 Agent」三类核心智能体协作链路：调度 Agent 汇总全部数据并生成调度方案，执行 Agent 将方案转换成具体设备、策略参数和执行位置，审计 Agent 对方案、执行动作和结果证据进行安全审计。系统最终形成从任务输入、方案生成、执行落位、审计验证到复盘沉淀的端到端闭环。

## 2. 目标场景与核心问题

目标场景：工业园区、商业综合体、充电站、工商业储能站点等微电网运营场景。

典型设备：

- 光伏发电
- 储能电池
- 充电桩
- 可控负荷
- 智能电表
- BMS / PCS / EMS
- 园区用电系统与告警系统

核心问题：

- 客户策略高度定制，无法复用。
- 光伏与负荷波动导致调度不稳定。
- 储能策略需要同时考虑成本、安全、寿命和供电可靠性。
- 调度结果缺少可解释依据、执行证据、审批机制和回滚路径。
- 普通 AI 看板只能展示数据，不能完成真正的业务闭环。

## 3. 方案概述

EnergyMesh Agents 将微电网调度拆成三层能力：

- Agent 协同层：基于 AgentTeams 编排三类 Agent 的身份、任务拆解、上下文传递、协同执行和状态追踪。
- Skill 能力层：把事件接入、策略生成、执行落位、审计验证、复盘沉淀封装为可复用 Skill。
- 工具连接层：通过 MCP 或等价工具契约连接 EMS、SCADA、数据库、仿真器、审批系统、审计日志和知识库。

系统在初赛阶段重点说明架构与闭环，复赛阶段可实现一个最小可运行 Demo：当光伏出力下降、储能设备告警且峰值电价临近时，系统自动生成调度方案，定位具体执行位置，经审计 Agent 审核后进入模拟执行，并输出完整证据包。

## 4. 多 Agent 架构

### 4.1 调度 Agent

身份定义：微电网策略规划者。

核心职责：

- 接收园区全量运行数据、客户目标、历史策略、设备约束和实时事件。
- 对齐客户目标，例如降本、削峰、保供、低碳、储能寿命优先。
- 生成一套或多套候选调度方案。
- 给出方案原因、预期收益、风险点和执行前置条件。

能力边界：

- 只生成方案和策略参数，不直接操作真实设备。
- 必须把候选方案交给审计 Agent 审核。
- 遇到数据不足时必须标注置信度并请求补充数据或降级为保守策略。

### 4.2 执行 Agent

身份定义：方案落地执行者。

核心职责：

- 接收调度 Agent 生成的方案。
- 将抽象方案转换成具体执行位置和参数变更，例如储能充放电功率、目标 SOC、可控负荷降载比例、充电桩限流策略、EMS 策略配置项。
- 调用设备接口、EMS 模拟器、配置系统或审批系统。
- 记录执行前状态、执行动作、执行结果和回滚点。

能力边界：

- 只能执行审计 Agent 放行的方案。
- 高风险动作必须等待人工审批。
- 执行失败时必须进入回滚或保守策略。

### 4.3 审计 Agent

身份定义：安全、合规与证据审计者。

核心职责：

- 审计调度 Agent 的候选方案是否违反安全规则和业务约束。
- 审计执行 Agent 的具体落点是否与已批准方案一致。
- 校验 SOC、功率边界、温度告警、关键负荷保障、备用容量和执行权限。
- 生成审计结论、风险解释、审批建议、回滚要求和证据包。

能力边界：

- 审计规则优先级高于经济收益目标。
- 不生成收益最优方案，只负责风险识别、拦截和证据沉淀。
- 对不可验证方案默认不放行。

## 5. AgentTeams 协同映射

EnergyMesh Agents 以 AgentTeams 作为协同设计基点。

| AgentTeams 能力 | EnergyMesh Agents 映射 |
| --- | --- |
| 角色编排 | 定义调度 Agent、执行 Agent、审计 Agent 三类身份和权限边界 |
| 任务拆解 | 将微电网事件拆为数据汇总、方案生成、执行落位、审计验证、复盘沉淀 |
| 上下文传递 | 在 Agent 间传递事件包、客户目标、设备约束、候选方案、审计结论和执行结果 |
| 协同执行 | 调度 Agent 生成方案，审计 Agent 审核，执行 Agent 落位执行，审计 Agent 复核 |
| 状态追踪 | 记录任务状态：已接收、已生成、待审计、待审批、执行中、已回滚、已完成 |
| 证据沉淀 | 保存 Trace、Log、Metrics、审批记录、执行前后状态和复盘报告 |

端到端闭环：

1. 系统接收微电网事件、客户目标和设备数据。
2. AgentTeams 创建任务上下文并分配给调度 Agent。
3. 调度 Agent 生成候选策略。
4. 审计 Agent 审核候选策略。
5. 需要修改时返回调度 Agent 重新生成。
6. 审核通过后，执行 Agent 将方案修改到具体位置。
7. 审计 Agent 复核执行结果和证据。
8. 系统生成复盘报告并沉淀为可复用 Skill 或策略案例。

## 6. 核心 Skill 清单

| Skill 名称 | 用途 | 输入与输出 | 调用条件 | 依赖工具 | 失败处理 | 安全边界 | 复用价值 | 协同关系 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `microgrid_context_ingest` | 汇总微电网运行上下文 | 输入设备数据、告警、电价、负荷、客户目标；输出标准事件包 | 新任务进入或数据更新 | EMS/SCADA/MQTT 模拟器、数据库 | 数据缺失时标注置信度并触发补数 | 只读数据，不执行控制 | 可复用于不同园区数据接入 | 为调度 Agent 提供统一上下文 |
| `dispatch_plan_generate` | 生成调度候选方案 | 输入事件包、约束、客户目标；输出候选方案、收益预测、风险说明 | 事件包完整或达到最低置信度 | 优化器、策略模板、历史案例库 | 优化失败时返回规则基线方案 | 不直接执行设备动作 | 沉淀行业策略生成能力 | 调度 Agent 核心 Skill |
| `execution_mapping` | 将方案映射到具体执行位置 | 输入候选方案、设备拓扑、配置 Schema；输出具体参数、目标设备、执行步骤 | 审计 Agent 初审通过后 | EMS 配置接口、设备模型、执行模拟器 | 找不到落点时退回调度 Agent 修改 | 不能越权修改未授权设备 | 可复用于不同 EMS/设备配置 | 执行 Agent 核心 Skill |
| `dispatch_audit_verify` | 审计方案与执行动作 | 输入方案、执行参数、安全规则；输出通过、拒绝或需审批 | 方案生成后、执行前后 | 规则引擎、仿真器、审计库 | 无法验证时默认不放行 | 安全规则优先于收益目标 | 可复用于所有高风险策略审核 | 审计 Agent 核心 Skill |
| `approval_rollback` | 管理审批与回滚 | 输入风险动作、审批人、回滚点；输出审批结果、回滚状态 | 高风险动作或执行失败 | 审批系统、执行日志、状态快照 | 审批超时进入保守策略 | 无审批不得执行高风险动作 | 可复用于生产级管控 | 连接执行 Agent 和审计 Agent |
| `postmortem_learn` | 复盘与经验沉淀 | 输入全链路证据；输出报告、经验规则、策略案例 | 任务完成、失败或回滚后 | 知识库、日志库、向量库 | 报告失败不覆盖原始证据 | 不得篡改历史审计 | 形成可复用调度知识 | 为后续调度 Agent 提供记忆 |

## 7. MCP 与工具集成设计

MCP 在本方案中承担工具连接层。若复赛阶段未完整实现 MCP Server，也会按等价契约设计，保证后续只需协议适配，不需要重写 Agent 与 Skill 链路。

| 工具名称 | 调用入口 | 参数 Schema | 返回结构 | 权限范围 | 失败重试 | 幂等控制 | 审计日志 | 降级方式 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `site_data_query` | MCP 或 HTTP API | `site_id, time_range, data_types` | 设备状态、负荷、电价、告警 | 只读 | 失败重试 3 次 | `request_id` | 记录查询范围 | 使用最近快照 |
| `dispatch_optimizer` | MCP 或本地服务 | `event_package, constraints, objective` | 候选方案与指标 | 只生成方案 | 求解超时降级 | `plan_id` | 记录约束和结果 | 使用规则基线 |
| `microgrid_simulator` | MCP 或本地仿真器 | `site_model, plan` | 仿真通过/失败、风险项 | 只读仿真 | 失败不重试执行 | `simulation_id` | 保存仿真证据 | 要求人工审核 |
| `ems_config_apply` | MCP 或 EMS 适配器 | `device_id, config_key, value, approval_id` | 执行状态、前后快照 | 受限写入 | 只对幂等动作重试 | `execution_id` | 保存执行证据 | 回滚到前状态 |
| `audit_evidence_write` | MCP 或数据库 | `task_id, trace, logs, metrics, files` | 证据包地址 | 写入审计库 | 失败告警 | `evidence_id` | 全量记录 | 本地落盘后补写 |

鉴权方式：

- 只读工具与写入工具分离授权。
- 执行类工具必须携带 `approval_id`。
- 所有工具调用保留 `task_id`、`agent_id`、`skill_name`、`trace_id`。

## 8. RAG 与上下文增强

本方案至少实现 3 项上下文能力：

- 共享状态管理：AgentTeams 维护任务状态、事件包、候选方案、审计结论、审批状态、执行状态。
- 轨迹可观测：记录 Agent 推理、Skill 调用、工具调用和人工审批轨迹。
- 知识库 RAG：检索历史策略案例、设备手册、安全规则、客户偏好和事故复盘。

RAG 在链路中的位置：

1. MCP 接入历史策略库、设备规则、客户配置和复盘报告。
2. Skill 封装检索、证据对齐和结果写入。
3. 调度 Agent 判断检索结果是否足够支持当前方案。
4. 审计 Agent 使用检索到的规则和历史事故校验风险。

## 9. 可观测设计

可观测覆盖 Trace、Log、Metrics 三类数据。

Trace：

- AgentTeams 任务链路
- Agent 输入输出
- Skill 调用链路
- MCP 工具调用链路
- RAG 检索链路
- LLM 推理摘要

Log：

- 事件接收日志
- 方案生成日志
- 审计拒绝或放行日志
- 审批日志
- 执行与回滚日志

Metrics：

- 调度任务完成率
- 工具调用成功率
- 平均处置时间
- 不安全方案拦截率
- 峰值负荷降低比例
- 储能 SOC 越界次数
- 运行成本变化

语义规范：

- Trace 字段参考 OpenTelemetry GenAI 语义规范设计。
- 每条记录包含 `trace_id`、`task_id`、`agent_id`、`skill_name`、`tool_name`、`latency_ms`、`status`、`risk_level`。

后端存储：

- 初赛设计：本地 JSONL / SQLite 证据包。
- 复赛实现：PostgreSQL 或 PolarDB for PostgreSQL 保存任务、向量、日志和审计证据。

## 11. Demo 设计与运行结果

Demo 场景：

> 14:00 光伏出力下降 35%，一台储能设备出现温度告警，园区 15:00 即将进入峰值电价。客户目标是在不影响关键负荷的前提下降低购电成本。

Demo 流程：

1. 输入模拟站点数据、设备告警、电价和客户目标。
2. 调度 Agent 生成三套方案：经济优先、稳健优先、保守保供。
3. 审计 Agent 否决过度放电方案。
4. 调度 Agent 修订方案并提交执行。
5. 执行 Agent 将方案映射到储能功率、负荷降载和充电桩限流配置。
6. 审计 Agent 复核具体执行位置和参数。
7. 高风险动作进入人工审批。
8. 审批通过后执行 Agent 在模拟环境执行。
9. 系统输出执行证据包和复盘报告。

计划展示指标：

- 峰值购电功率下降
- 关键负荷保障率保持 100%
- 不安全方案被拦截
- 储能 SOC 未越界
- 完整 Trace、Log、Metrics 可回放
